## 2. 把它写成可检验的问题

**目标函数**:在满足下列约束的前提下,最小化
`一次性本地硬件成本(按月摊销) + 每月云端服务费 + 流量费`。

| 约束 / 指标 | 说明 |
|---|---|
| 单次延迟(含传输) | 最终北极星是"1 秒内";不同任务应分别定义预算(见 project-goals.md §5)。现阶段先把"能做到多少"测清楚 |
| 断网 / 弱网可用性 | 应用场景含森林、山谷、田野(project-goals.md §4),网络可能很差甚至没有——本地必须有降级结果,云只能是增强而不是依赖 |
| 隐私 | 摄像头画面是否离开设备。Google 官方条款:付费 API 不用提示词和图片改进产品;**免费档会用于改进产品且可能被人工审核**——用户画面绝不能走免费档 |
| 云服务月预算 | ≤ 100 加元(调研约束,见上) |
| 本地硬件对产品价格的影响 | 用户明确担心"GPU 本地化会大幅抬高产品价格" |
| 成本与开源优先 | AGENTS.md 第17条 |

## 3. 两股相反的力

- **远程**:算力便宜、按需;代价是传输(带宽、抖动、覆盖)、隐私、持续月费、依赖连接。
- **本地**:无传输、可离线、隐私好;代价是硬件成本抬高产品价格。2026 年边缘硬件
  因内存涨价更贵(见 §5:Jetson Orin Nano Super 从 $249 涨到 $399,Raspberry Pi 5
  16GB 标价 $305)。
- **手机端侧 NPU**:如果产品形态可以是手机应用,额外硬件成本为零(你已有 VIVO 与
  iPhone),但至今**没有在你的设备上实测过**,是最大的未验证点。

## 4. 策略假设(待数据验证,**不是结论**)

- **H1 分层**:本地常驻轻量层(帧差门控 + 粗略概况)决定"是否值得上传"并在断网时
  兜底;云端按需做重理解。
- **H2 传关键帧,不传视频流**:场景理解不需要连续视频。实测 JPEG 中位数:640×480
  约 51.7 KB、480×360 约 34.2 KB、320×240 约 17.8 KB。在**假设**的上行 1/5/20 Mbps
  下,640×480 单张传输约 0.41/0.08/0.02 秒;每天 2,000 张约 3.1 GB/月。传输在
  "关键帧 + 正常网络"下不是瓶颈;真正的风险是**覆盖缺失、抖动**,以及**连续视频流**。
- **H3 事件触发时,按次计费的托管 API 比摊销本地加速器便宜得多**:按
  `scripts/cost_model.py`(640×480,假设 100 个文本提示 token + 60 个输出 token),
  Gemini 3.5 Flash-Lite 约 $0.00049/次(约 0.70 加元/千次)。2,000 次/天 ≈ 41.9 加元/月;
  100 加元预算大约支持每天 4,800 次。Jetson Orin Nano Super($399,按 24 个月摊销)
  相对它的盈亏平衡点约 1,130 次/天——**前提是这块硬件真能达到所需质量,目前未验证**。
  因此从纯费用角度远程占优,约束来自连接、延迟抖动和隐私,而不是钱。
- **H4 常驻 24 小时的 GPU 基本超预算**:RunPod 社区云 4090 $0.34/小时,24 小时 ≈ 349
  加元/月;每天 2 小时 ≈ 29 加元。按秒计费的 serverless 更适合零散使用,但有冷启动。

## 7. 暂定决策框架(数字待实验补全)

- 产品**必须能离线**:本地层要独立给出概况(候选:手机 NPU、CPU 上的小模型、小型加速器),云只做增强。
- 产品**基本联网**且事件率低(每天数百到几千次):托管 API 按次计费最便宜,本地只做门控。
- 值得买本地加速器的条件:事件率高到摊销成本低于云月费(盈亏平衡见 cost_model.py),并且离线或隐私需求强。
- 云 GPU **常驻**通常超过 100 加元预算;仅在需要自托管开源模型(隐私、定制)时按小时租用。

## 8. 第二条目标:本地方案"极致化"审计(2026-10-03 补充)

用户原意:希望把本地这条线做到极致——当前模型和当前本地配置**是否已经调到最优、最快**,
或者**本地方案本身是不是最好的**。这是第 2 节目标函数里"本地层"的上限问题:本地层
越快、越好,需要上云的比例越低,成本平衡点就越偏向本地。

**先承认一个会改变结论的错误**:我 2026-09-29 判断"Iris Xe 的 SYCL/OpenCL 路径(单帧
约 5.4–8 秒)没有明显优于 CPU(约 4.5 秒)",但那个"CPU 4.5 秒"基线是缩图或缓存命中的
数字,新图 640×480 在 Ollama 默认配置下实际是 **16.8 秒**。若拿 16.8 秒对比,当时那条
iGPU 路径(同样是 640×480 新图)反而可能快 2 倍以上;而生产用的 Ollama 又**不能**把视觉
编码放到核显上。**这只是重新解读旧数据,不是结论**,必须用同一批帧、同一提示词、同一
JSON schema 做受控对照后才能下结论。

这条已经升级为**长期规则**:AGENTS.md 第 31 条"Benchmark Optimality Audit"——之后每一轮
基准都必须附审计表,覆盖模型、参数、引擎/硬件、方法/架构、基线有效性、对成本平衡的影响。
"最优"只能说"在我测过的配置里最优",不能说全局最优。本轮审计清单与状态(2026-10-03):

| 杠杆 | 状态 | 说明 |
|---|---|---|

## 9. 风险与不确定性

- 价格变化快(Jetson 三个月涨 60%);所有价格都带查询日期,结论会过期。
- 厂商延迟、token 数、"几十毫秒"等均为声称,**必须实测后才能进入决策**。
- 免费 API 档会把画面用于改进产品;任何涉及用户画面的测试只能用付费档并先核对条款。
- 盈亏平衡只比较了费用,没有计入电费、运维、硬件故障和开发成本,也没有验证本地加速器能否达到所需质量。
- 本地延迟的测量条件(Ollama 默认线程、单机、单次会话)可能与最终产品不同。
