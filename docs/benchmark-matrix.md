## 测试方法(保证矩阵内数字可比较)

固定变量,只改硬件/后端这一个维度:
- 模型:MiniCPM-V 4.6(Q4_K_M 量化)
- 场景:单帧图像理解,提示词要求极短输出(yes/no 或 ≤10 token)
- **关键方法修正(2026-09-29 发现)**:必须使用**每次不同的新图片**测试,
  不能重复发送同一张图——重复发送同一张图会命中内部缓存,得到虚假的
  乐观数字(我们自己踩过这个坑,见下方"已知方法陷阱")
- 记录:端到端耗时(从发出请求到拿到响应),不单独拆解编码/解码阶段
  (除非工具本身能提供这个拆分)

## 已知方法陷阱(如实记录,别人复现时也会踩到)

1. **图像缓存效应**:同一张图片重复发送,第2次起会显著变快(我们测到
   4.5秒→2.2秒),这是引擎内部缓存命中,不代表真实处理新画面的速度。
   矩阵里的数字必须是"每次都是新图片"的结果。
2. **模态切换开销**:在"纯文字请求"和"图文请求"之间切换,切换后的第一次
   调用会有额外几秒到十几秒的开销(推测是重新初始化视觉编码路径),矩阵
   测试应该保持同一种模态连续测,避免把这个开销误算进"稳定状态"里。
3. **`num_thread` 等模型加载参数,改动会触发重新加载**:测线程数效果时,
   不能在同一批测试里频繁改这个参数,否则测到的是"重新加载耗时"而不是
   "该线程数下的真实推理速度"。

## 方法学确认:不同后端下模型输出内容是否一致(2026-09-29)

在比较不同硬件/后端的延迟之前,先确认了一件更基础的事:**换后端会不会
连带换了模型本身的判断能力**?已核实:

- Ollama 拉取的 `minicpm-v4.6` 和手动从 ggml-org 下载的 GGUF 都是
  **Q4_K_M** 量化(通过 `ollama show --modelfile` 和 `/api/show` 确认,
  语言模型部分参数量 752.16M,对得上),不是两个不同量化等级在比较
- 目前所有事实性判断题(如"图里有没有人")在 Ollama/CPU 和 llama.cpp
  SYCL/OpenCL 两条路径下**回答内容一致**,没有出现前后矛盾
- **尚未验证**:同一段"详细场景描述"提示词在两条路径下的输出内容是否
  逐字一致或至少语义等价——目前只针对简单判断题做了交叉验证,更复杂的
  开放式描述还没有专门对比过,如果需要严格结论,这里还要补一轮测试
- 结论:目前的矩阵在比较"同一个模型、同一个量化等级"在不同硬件/后端下
  的速度,这个比较是有效的,不是在比较不同能力的模型

   这一档的真实数字,而且能顺便验证云GPU路线到底能不能满足"1秒内"这个
   目标

这两个数据点分别代表"利用现有硬件能做到多好"和"加一点预算能做到多好",
两条线加起来就是一张有意义的矩阵雏形,以后再补其他硬件档位(比如手机端侧

## Iris Xe 实验结论

**方法确认**:通过 `ollama show`/`api show` 核实,Ollama 和手动下载的 GGUF
都是同一个 Q4_K_M 量化,且事实性判断题("图里有没有人")在两条路径下
回答内容一致——比较的是同一个模型,只是硬件加速方式不同。

**耗时构成分析**:MiniCPM-V 4.6 的视觉部分是 **SigLIP2-400M** 编码器,配合
**LLaVA-UHD 自适应分块**——不是整图一次性编码,而是先切成多个"瓦片"
(我们这张640x480测试图被切成 **7块**,来自 `llama-mtmd-cli` 的详细日志
`n_chunks = 7`),每块单独跑一次 ViT 前向传播。服务器返回的 `timings` 显示
纯文字生成(reasoning+答案,约59个token)只花了约1.9秒(≈30 token/秒,
GPU确实比CPU解码快),**端到端5.4-5.6秒里,剩下约3.5秒的缺口没有被计入
`timings` 字段,推断就是视觉编码器跑7块瓦片的真实计算耗时**——这是算力
密集型计算,粗算量级(96EU、约2 TFLOPS FP32理论峰值,实际有效利用率打
折扣)和观测到的3-5秒是吻合的。也就是说,**这不是软件没调好,是这块
核显的原始算力对这个任务量级来说就是这个水平**。

**尝试的优化:限制 `--image-max-tokens` 到64(反直觉的负面结果)**:
猜测"少给点token预算=少切几块=算得快",结果反而更慢(7-8秒,比默认配置
还慢2-3秒)。可能的原因(尚未深入验证,列为待查):MiniCPM-V 论文里提到
默认对1.8M像素图像用约640个token,64是远低于模型原生训练配置的数值,
可能反而逼着自适应分块算法切出**更多、更小**的瓦片来凑token预算,而不是
真的减少计算量。**结论:这个参数不是简单的"越小越快"旋钮,盲目调低没有
用,如果要继续深挖需要理解分块算法的具体逻辑,不是黑盒试参数能搞定的**。

**单帧结论**:目前在这台机器上,GPU(Iris Xe/SYCL/OpenCL)路径单次孤立
请求最好结果约5.4-5.6秒,并**没有明显优于CPU的~4.5秒基线**——瓶颈(视觉
编码算力)对两种后端都成立。继续抠单帧延迟细节(改批处理大小、试Vulkan
后端、等驱动更新)属于收益递减区间,不建议继续投入。

## 并发实验结论(2026-09-29,重要发现)

单帧延迟压不下去,但"处理一整段视频"这个真实场景不需要一帧一帧排队等。
llama-server 默认支持多个并行槽位(启动日志显示 `n_slots = 4`),测试方法:
从录制视频里取8个不同时间点的帧,分别测"顺序处理总耗时" vs "并发处理
总耗时":

| 并发数 | 8帧总耗时 | 等效单帧耗时 | 相对顺序处理 |
|---|---|---|---|
| 1(顺序,`--parallel 4`但一个个发) | 73.84秒 | ~9.2秒/帧 | 基准 |
| **4**(`--parallel 4`,4路同时发) | **14.62秒** | **~1.8秒/帧** | **5.05倍加速** |
| 8(`--parallel 8`,8路同时发) | 58.42秒 | ~7.3秒/帧 | 比4路慢4倍(负结果) |

**关键发现**:4路并发是这块 Iris Xe GPU 的"甜点"——已经把真实并行计算能力
用满,超过4路(测了8路)会导致资源争抢,总吞吐量反而变差,不是"并发越多
越快"。回答内容在并发下依然保持一致、正确,没有质量下降。

**对项目的实际意义**:Stage 1 处理一整段视频时,不应该像目前 spec 里写的
那样把 chunk 一个个顺序丢给模型(`src/visualintel/cli.py` 的 `cmd_report`
目前是 `for chunk in chunks` 顺序调用),而应该**以4个为一批并发处理**——
这是这次探索里对实际项目最直接可用的优化,应该体现进 Stage 1 的实现里
(比单纯追求单帧延迟更有实际价值)。

## 总体结论

单帧延迟这台机器已经探到头(~4.5-5.6秒,CPU/GPU差距不大),继续在这个
维度优化收益递减。但"4路并发处理批量chunk"这个发现,把**处理一整段视频
的实际吞吐量**从"单帧耗时的总和"降到了约1/5,是目前为止最有性价比的
优化,而且不需要新硬件、不需要盲调黑盒参数,应该直接吸收进 Stage 1 的
实现计划。要继续往"单帧1秒以内"逼近,大概率还是要靠算力量级更大的硬件
(独立/云端GPU),但"处理一整段视频要多久"这个更贴近实际需求的指标,
现在已经有明显改善。

## 本地硬件探索完整收尾(2026-09-29)

这一轮针对"能不能在本机把速度做到极致",系统性试过的东西汇总(如实列出
成功和失败,不挑好看的说):

| 尝试 | 结果 |
|---|---|
| Ollama 纯CPU | ✅可用,~4.5秒/新图,基线 |
| Ollama + 核显 | ❌不可行,Ollama对共享显存GPU硬性禁止offload视觉编码器,无法绕过 |
| llama.cpp SYCL + Level-Zero后端 | ❌崩溃(`UR_RESULT_ERROR_DEVICE_LOST`驱动级错误) |
| llama.cpp SYCL + OpenCL设备选择器 | ✅可用,~5.4-5.6秒/新图,和CPU基线相近 |
| 降低输入图片分辨率 | ❌无效,模型自适应分块逻辑与输入像素数无关 |
| `--image-max-tokens` 调低到64 | ❌反而更慢(7-8秒),不是简单的"越小越快"旋钮 |
| **4路并发处理多个chunk** | ✅**有效,5.05倍吞吐量提升**,已吸收进 Stage 1 实现计划 |
| 8路并发 | ❌比4路更慢,GPU资源争抢,负结果 |
| llama.cpp Vulkan 后端 | ❌崩溃(`ggml-backend.cpp:941`张量分配错误),这个构建版本不兼容 |

**最终结论**:在这台无独立显卡的笔记本上,单次请求的延迟地板大约是
4.5-5.6秒,这是视觉编码器(SigLIP2-400M,7块瓦片)的真实计算量决定的,
不是配置问题,尝试过的软件层优化(分辨率、token预算、不同GPU后端)都
没能突破这个地板。**唯一真正有效的优化是并发**——不降低单次延迟,但让
处理一整段视频的总耗时降到约1/5。如果还想继续逼近"单帧1秒以内"这个
最初的目标,已知走完的路径里没有答案,下一步要么是换算力量级明显更大的
硬件(独立/云端GPU,此前已经确认可以按需租用),要么是换一个不做自适应
高分辨率分块、拿细节换速度的更简单模型(比如 Moondream,尚未测试),
要么是把"快速判断"和"完整理解"拆成两层架构(用YOLO/decider-2b-vision
这类真正的毫秒级模型做前置门控)。这三条路线本次探索都还没有验证,列为
后续候选。
