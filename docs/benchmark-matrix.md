# 硬件能力矩阵:不同硬件档位下的视觉理解延迟(草案 v0.1)

> 目的:不是"把某一台机器榨到极限",而是搞清楚"要达到某个延迟目标,大概
> 需要什么档位的硬件"——用于回答"最低配置要求是什么"这类问题。
> **标注规则(严格执行,不得混淆,AGENTS.md 第4条)**:
> - ✅**实测** = 我们自己在这台项目环境里真实跑出来的数字,可复现
> - 📄**第三方报告** = 从搜索/文章里看到的别人的数据,我们没有验证过,
>   仅供参考方向,不能当作确定结论引用
> - ❓**待测** = 计划要测但还没做

## 测试方法(保证矩阵内数字可比较)

固定变量,只改硬件/后端这一个维度:
- 模型:MiniCPM-V 4.6(Q4_K_M 量化)
- 场景:单帧图像理解,提示词要求极短输出(yes/no 或 ≤10 token)
- **关键方法修正(2026-09-29 发现)**:必须使用**每次不同的新图片**测试,
  不能重复发送同一张图——重复发送同一张图会命中内部缓存,得到虚假的
  乐观数字(我们自己踩过这个坑,见下方"已知方法陷阱")
- 记录:端到端耗时(从发出请求到拿到响应),不单独拆解编码/解码阶段
  (除非工具本身能提供这个拆分)

## 已知方法陷阱(如实记录,别人复现时也会踩到)

1. **图像缓存效应**:同一张图片重复发送,第2次起会显著变快(我们测到
   4.5秒→2.2秒),这是引擎内部缓存命中,不代表真实处理新画面的速度。
   矩阵里的数字必须是"每次都是新图片"的结果。
2. **模态切换开销**:在"纯文字请求"和"图文请求"之间切换,切换后的第一次
   调用会有额外几秒到十几秒的开销(推测是重新初始化视觉编码路径),矩阵
   测试应该保持同一种模态连续测,避免把这个开销误算进"稳定状态"里。
3. **`num_thread` 等模型加载参数,改动会触发重新加载**:测线程数效果时,
   不能在同一批测试里频繁改这个参数,否则测到的是"重新加载耗时"而不是
   "该线程数下的真实推理速度"。

## 方法学确认:不同后端下模型输出内容是否一致(2026-09-29)

在比较不同硬件/后端的延迟之前,先确认了一件更基础的事:**换后端会不会
连带换了模型本身的判断能力**?已核实:

- Ollama 拉取的 `minicpm-v4.6` 和手动从 ggml-org 下载的 GGUF 都是
  **Q4_K_M** 量化(通过 `ollama show --modelfile` 和 `/api/show` 确认,
  语言模型部分参数量 752.16M,对得上),不是两个不同量化等级在比较
- 目前所有事实性判断题(如"图里有没有人")在 Ollama/CPU 和 llama.cpp
  SYCL/OpenCL 两条路径下**回答内容一致**,没有出现前后矛盾
- **尚未验证**:同一段"详细场景描述"提示词在两条路径下的输出内容是否
  逐字一致或至少语义等价——目前只针对简单判断题做了交叉验证,更复杂的
  开放式描述还没有专门对比过,如果需要严格结论,这里还要补一轮测试
- 结论:目前的矩阵在比较"同一个模型、同一个量化等级"在不同硬件/后端下
  的速度,这个比较是有效的,不是在比较不同能力的模型

## 下一步:怎么把矩阵填满

要往下填,需要真的拿到对应档位的硬件跑一遍,不能靠猜。现实可行的两条路
**可以都做,不互斥**:

1. **本机 + Iris Xe(SYCL)**——不需要新硬件,装 llama.cpp 的 SYCL 版本,
   把现有测试方法跑一遍,得到"核显加速"这一档的真实数字
2. **租一台云 GPU**——花一小时租金,跑同一套测试方法,得到"入门级GPU"
   这一档的真实数字,而且能顺便验证云GPU路线到底能不能满足"1秒内"这个
   目标

这两个数据点分别代表"利用现有硬件能做到多好"和"加一点预算能做到多好",
两条线加起来就是一张有意义的矩阵雏形,以后再补其他硬件档位(比如手机端侧
NPU、真正的独立显卡等)。

**已确认(2026-09-29)**:先做①Iris Xe SYCL 这一项,云GPU②留待之后。

## 当前实验记录:Iris Xe + SYCL(2026-09-29,进行中)

**为什么选 SYCL,不是继续调 Ollama**:已确认 Ollama 在所有共享显存的核显/
APU 系统上都硬性禁止把视觉编码器offload到GPU(防OOM的保守策略),截至
Ollama 0.34.4 没有环境变量能绕过。要用上这台机器的 Iris Xe(96 EU,超过
SYCL"可用"门槛80 EU),必须换成 llama.cpp 的 SYCL 后端,绕开 Ollama。

**具体素材(可复现,来源均为官方发布)**:
- `llama.cpp` Windows SYCL 预编译版:build `b11146`,文件
  `llama-b11146-bin-win-sycl-x64.zip`,120,194,517 字节(约114.6MB),来自
  <https://github.com/ggml-org/llama.cpp/releases/download/b11146/llama-b11146-bin-win-sycl-x64.zip>。
  该包自带 oneAPI 运行时 DLL,不需要另装 Intel oneAPI 工具链。
- 主模型:`MiniCPM-V-4.6-Q4_K_M.gguf`,529,101,536 字节(约504.6MB),来自
  <https://huggingface.co/ggml-org/MiniCPM-V-4.6-GGUF/resolve/main/MiniCPM-V-4.6-Q4_K_M.gguf>
- 视觉投影文件:`mmproj-MiniCPM-V-4.6-Q8_0.gguf`,727,954,528 字节(约694.3MB),来自
  <https://huggingface.co/ggml-org/MiniCPM-V-4.6-GGUF/resolve/main/mmproj-MiniCPM-V-4.6-Q8_0.gguf>
- 三个文件合计约 1.31GB,下载到本机 scratchpad 临时目录(不进 git 仓库)

**计划步骤**:
1. 下载上述三个文件(进行中)
2. 解压 llama.cpp SYCL 包
3. 用其中的多模态命令行工具(`llama-mtmd-cli` 或同名工具),通过 `-ngl` 参数
   把计算层offload到 Iris Xe,加载主模型+mmproj
4. 用和 Ollama 测试同一张新图片(遵守上面"已知方法陷阱"里的规则:不重复
   发送同一张图、不在测试中途混用文字/图像模态)测一次端到端耗时
5. 把结果填回上面的矩阵表格,注明 ✅实测,并与 CPU-only 的 ~4.5秒 基线对比
