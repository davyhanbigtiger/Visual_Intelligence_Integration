# 云 GPU(Tesla T4)实测与最优性审计(2026-10-04)

> 范围:腾讯云东京、GN7.2XLARGE32(1×Tesla T4 16 GB、8 vCPU、32 GiB),Ubuntu 24.04.4、驱动 580.126.20。
> 价格是用户提供的 **1.54 元/小时**(竞价/低库存,"2折",未对照账单核实)。只发送公开 COCO 图和合成圆图,
> **没有任何个人画面离开本机**。输入、提示词(`SCENE_PROMPT` + JSON schema)、采样(temperature 0、seed 42、
> 最多 96 token)与本机测试相同;每档 12 张不同新图、1 次丢弃的热身,n 很小,只报描述统计。
> 原始记录:`outputs/cloud-t4-20261004/*/records.jsonl`、`summary.json`,服务器侧日志在 `server/`(均被 git 忽略)。
> 质量判断全部是**助手自行核对,非用户独立验收**。

## 0. 摘要

- **MiniCPM-V 4.6 在 T4 上端到端约 1 秒**(从加拿大经 SSH 隧道到东京,含约 0.4 秒往返):llama.cpp 640 档中位
  **0.96 秒**、448 档 0.72 秒;Ollama 640 档 1.23 秒、448 档 0.98 秒。服务器端纯计算约 0.4–0.8 秒。
  相同的 12 张图,本机核显路径是 3.2–6.8 秒;按同一引擎比较,640 档远程 T4 比本机核显快 **Ollama 约 4.8 倍
  (5.85 → 1.23 秒)、llama.cpp 约 7.1 倍(6.82 → 0.96 秒)**,且 T4 的数字已含约 0.4 秒往返。
- **瓶颈不再是计算,而是往返时延。** 隧道 GET 往返中位 **0.39–0.40 秒**,正好等于请求的"网络开销"(墙钟减去服务器耗时,
  0.39–0.40 秒,与图片大小无关)。上传 17–52 KB 的 JPEG 在这条链路上测不出额外耗时。
- **成本:** 24 小时常驻 T4 约 1109 元/月 ≈ **236 加元/月**(1 元 ≈ 0.2125 加元,🏷 Bank of Canada 2026-10-02 的搜索摘要),
  超出 100 加元预算,也只有在每天超过约 1.1 万次事件时才比 Gemini Flash-Lite 的按次计费便宜(见 §3)。
- **一个重要的可靠性发现:** Ollama 偶发输出"坐标乱码"(非法 JSON)——本机 Vulkan 核显顺序请求 3/24,T4 CUDA 的 8 路并发 2/23;
  **llama.cpp 在 271 个请求里 0 个**。所以问题出在 Ollama 的运行器路径,不是模型或提示词,也不是某一种 GPU 后端(§2.8)。
- **更正我自己的几处错误**见 §6(其中最重要的:llama-server 第一轮其实跑在 CPU 上;之前说乱码是"Vulkan 特有"不成立)。

## 1. 方法与前提

- 路径:笔记本 → SSH 隧道(本机 21434→服务器 Ollama,28080→llama-server)→ 服务器 `127.0.0.1`。服务只监听回环地址。
- 软件(固定版本):Ollama v0.35.1(`OLLAMA_NUM_PARALLEL=4`)、llama.cpp b11146(CUDA 12.8 包,`--parallel 4 -c 8192`、
  `-ngl 99`、Q4_K_M + mmproj Q8_0 GGUF,`--reasoning off --jinja`)。
- 套件:`scripts/cloud/run_cloud_suite.py`(t0 往返、t1 延迟、t2 并发、t3 合成圆计数、t4 冷启动)。
- **计时口径差异:** Ollama 的 `total_duration` 含视觉编码;llama-server 的 `timings` 只含 prompt/生成,**不含视觉编码**。
  所以"网络开销"在 Ollama 一栏是纯网络(≈RTT),在 llama.cpp 一栏混有约 0.1 秒视觉编码,两者不可直接比较。
- 地理:加拿大西海岸到东京的往返约 0.4 秒。换成更近的区域,端到端会更短,但**没有测过**。

### 2.8 非法输出("坐标乱码")——跨引擎比较

典型输出:`…outdoor setting100 211 998 989` 或 `…shoreline0 100 998 200stand-up`,有时还泄漏 `</think>`;一直写到 96 token 上限被截断,JSON 不合法。

| 运行 | 请求数 | 非法 |
|---|---|---|
| 本机 Ollama + Vulkan 核显(顺序) | 24(COCO)| **3** |
| 同样 6 个请求,本机 Ollama 纯 CPU | 6 | 0 |
| T4 · Ollama · 顺序(5 个模型,t1/t3/t4) | 约 270 | 0 |
| T4 · Ollama · 8 路并发(两次) | 46 | **2** |
| 本机 llama.cpp SYCL 核显 | 24 | 0 |
| T4 · llama.cpp CUDA(顺序 + 并发 + 参数扫描)+ CPU 回退轮 | 271 | **0** |

结论(证据支持):乱码只出现在 **Ollama** 上,在两种完全不同的后端(Vulkan 和 CUDA)和两种负载(顺序和并发)下都出现过;
llama.cpp 在 271 个请求里没有。Ollama 的触发条件我没有查清——顺序的 T4 请求没出过,并发和 Vulkan 出过。
**我之前在本机文档里写的"Ollama 的 Vulkan 路径特有"不成立**,已在其他文档里更正。
对产品的含义:无论用哪种引擎,都应校验 JSON 并在失败时重发一次;若可选,llama.cpp 更可靠。

- **按需租用**(只开测试/高峰时段):1 小时约 0.33 加元;但这次从开机到可用约 15 分钟(主要是下载 19 GB 模型),
  再加上模型冷启动几十秒,所以不适合"一次事件开一次机"。预制镜像能缩短准备时间,**没有测过**。
- **价格敏感度很大:** 第三方聚合站(未核实)给出的标准按量价约 7.81–8.68 元/小时,是你这台价格的约 5 倍;
  按那个价格,所有上面的盈亏平衡点都要乘以约 5,结论会反过来。竞价实例还可能被回收或库存不足。
- 只算了实例费;未计公网流量、云盘、快照,也没有计开发和运维成本。

## 4. 对目标的含义(证据支持的部分 + 推断,都不是最终决策)

- **事实:** 在 T4 上 MiniCPM-V 4.6 的计算本身约 0.4–0.8 秒,"1 秒内"在计算上可达;端到端 0.7–1.2 秒,其中约 0.4 秒是往返。
- **事实:** 图片大小不是主要因素(往返时延主导);降到 448 以下单块,在 GPU 上只省约 0.2–0.25 秒,代价是更多无依据断言(本机已测)。
- **推断:** 24 小时独占一块 T4 不符合"每月 ≤100 加元";低频(≲1 万次/天)用按次 API,中高频才轮到自建 GPU。
- **推断:** 本机核显路径(3–7 秒)作为"离线兜底 + 事件筛选"层仍有价值,云端只处理被筛出来的关键帧。
- **未验证:** 托管 API 的真实端到端延迟、更近区域的往返时延、手机端侧 NPU、预制镜像的启动时间。

## 6. 本轮的错误与更正

1. **llama-server 第一轮其实跑在 CPU 上。** `libggml-cuda.so` 缺 `libcudart.so.12`/`libcublas.so.12`,服务器照常响应健康检查,
   却悄悄退回 CPU(640 档 17.8 秒)。我的安装脚本只检查了 `llama-server` 本身,没检查 CUDA 后端库;修复时又先错写了
   cudart 压缩包的解压路径(漏了 `--strip-components=1`),再把"日志里要有 CUDA"当判据,而这个版本根本不打印 CUDA 字样。
   现在改成:检查后端库依赖,并用 `nvidia-smi` 确认 llama-server 是 GPU 计算进程。那一轮数据保留在 `llama-baseline/`,标注为 CPU 回退。
2. **并发测试的缺陷:** 第 1 档用的图片尺寸与 t1 相同,可能命中缓存;且没有预热,模型冷加载会落进第 1 档。已修,Ollama 并发项重跑。
3. **预检误报:** `registry.ollama.ai` 根路径返回 404,被当成"连不上"。已改为任何 HTTP 状态都算可达。
4. **"乱码是 Ollama Vulkan 特有"的说法不成立**(见 §2.8),已在延迟文档、README 和目标文档里更正。

  已改成自动合并相同像素的档位、列标题显示真实分辨率;四个公开 NASA 视频都只有 320 宽,要看高分辨率需用 COCO 图(§2.1)或合成视频。
- **产品命令实测:** 未改协议的 `visualintel scene` 通过翻译层读公开视频,整条命令(含 Python 启动和视频解码)约 1.2–2.5 秒,
  一次 3.6 秒;描述合理。**摄像头 demo 和多帧命令(`report`、`ask`)没有在远程上跑过。**
- **连接复用的 A/B(24 对,交替,未命中缓存,尺寸 560–584):** 翻译层用连接池复用上游连接 **0.679 秒**,
  直连隧道每次新建连接 **0.865 秒**,中位数每次省约 **0.19 秒**。也就是说 §0 里"约 0.4 秒往返"有一部分是每次新建连接穿过隧道的开销,
  不是纯网络。同一批请求里最快的一次 0.395 秒,说明纯网络往返应当低于 0.2 秒(`ping` 没有拿到结果,未直接测量)。
- **用户的摄像头实测(2026-10-04):** 用户在自己的 Windows 11 摄像头上,用 `visualintel camera` 经翻译层连 T4(远程方式),
  反馈"结果好,速度也可以",窗口里显示的耗时**大约 1.3 秒**。这是用户口头转述的粗略数字(次数、摄像头分辨率、
  是否含首次请求均未记录),不是受控测量;它比上面受控测试的 0.68–0.96 秒高约 0.3–0.6 秒,原因未查
  (可能因素:摄像头画面内容和尺寸不同、窗口界面线程、首次请求预热、隧道空闲后连接重建、当时的网络,均未验证)。
  该次测试发出的是用户本人的摄像头画面,经用户明确选择,实例终止后随之销毁。
- 部署方式:`scripts/cloud/connect_remote.ps1`(隧道 + 翻译层,`-Stop` 只结束自己启动的进程)、
  `scripts/cloud/start_local_llama.ps1`(本机 llama.cpp 启停)。引擎只改了一处:环境变量 `VISUALINTEL_OLLAMA_URL`
  可指定模型地址,**默认不变**,且默认只接受回环地址(非回环需再设 `VISUALINTEL_ALLOW_NONLOOPBACK=1`)。138 个测试全部通过。
- 限制:远程 llama-server 目前是 `--parallel 4 -c 8192`,每个槽位只有 2048 token 上下文,多帧提示可能被拒;
  需要时用 `restart_llama.sh --parallel 1 -c 8192` 重启。

## 8. 局限

- 单个实例、单次会话、每格 n=12;COCO 图只有一类场景风格,不代表真实使用画面。
- 往返时延是加拿大西海岸到东京经 SSH 隧道的值,隧道本身可能增加开销;换用直连或更近区域会不同。
- 价格是用户提供的竞价价,未对照账单;汇率来自搜索摘要转述。
- 质量评估是助手自评,抽查样本很小。
- 本机与云端不是同一引擎栈,"GPU 比核显快 N 倍"只能在同一批图上做描述性比较。
