# 本机场景描述延迟:受控实测与最优性审计(2026-10-03)

> 范围:MiniCPM-V 4.6 Q4_K_M,生产场景提示词(`SCENE_PROMPT` + `FACTUAL_SCHEMA`,
> temperature 0、seed 42、最多 96 token),单次请求一张图。机器:i7-1355U(10 核/12 线程)、
> Iris Xe 核显、15.7 GB 内存、Windows 11。数据保存在 `outputs/`(被 git 忽略)。
> 质量判断全部是**助手自行核对画面,非用户独立验收**。n 很小,只报描述统计,不做显著性声称。

## 1. 先更正我自己之前的错误

我 2026-09-29 的文档里有两处把别的东西当成了"640×480 新图的速度":

- "稳态约 2.2 秒"是**同一张图重复发送的缓存命中**;
- "448/336/224 缩图约 4.5 秒"是**缩小后只切一块**的新图,不是 640×480 的速度。

同一天 Ollama 自己的日志里,640×480 新图请求就是 10–12 秒。由此得出的"分辨率无效""核显路径
没有明显优于 CPU""单帧已探到头"都**不成立**,以本文数据为准。

## 2. 方法

- 每张图在同一条件内只用一次(图片缓存会造假);先做 1 次丢弃的热身;顺序执行;条件顺序按
  拉丁方轮换;记录机器状态。输入帧来自 `videos/test_video.avi` 均匀抽取(含人脸,仅本地)。
- 脚本:`scripts/benchmark_scene_latency.py`(Ollama)、`scripts/evaluate_llama_scenes.py`
  (llama.cpp,新增 `--gpu`、`--server-arg`、`--prompt`、`--warmup`,默认行为不变)、
  `scripts/diagnose_request_variants.py`。辅助函数有单元测试。

## 3. 结果

### 3.1 Ollama(生产路径,CPU)× 输入尺寸 — n=12 张新图/档

| 最长边 | 单次中位数(最小–最大) | `prompt_eval` 中位 | 视觉 token | JPEG 中位 | 合法 JSON |
|---|---|---|---|---|---|
| 640 | **16.8 秒**(15.7–17.8) | 13.8 秒(约 82%) | 294 | 51.7 KB | 12/12 |
| 480 | 17.2 秒(15.9–22.0) | 14.1 秒 | 285 | 34.2 KB | 12/12 |
| 320 | **7.7 秒**(7.3–11.7) | 4.5 秒 | 151 | 17.8 KB | 11/12 |

生成约 25 个 token 只要约 1 秒。同一张图重复发送 5 次:2.75–2.98 秒(缓存命中,仅作对照)。

### 3.2 分块阈值(n=8/档)

| 最长边 | 中位数(最小–最大) | 视觉 token | 合法 JSON |
|---|---|---|---|
| 480 | 17.1 秒(15.9–18.6) | 285 | 8/8 |
| **448** | **7.7 秒**(7.4–8.5) | **151** | 8/8 |
| 416 | 7.8 秒(7.5–8.7) | 151 | 8/8 |
| 384 | 8.2 秒(7.8–13.2) | 151 | 6/8 |

**阈值在最长边 448 与 480 之间**:≥480 把图切成多块(285–294 token),≤448 只切一块(151 token),
耗时差约 2.2 倍。448 是最大的单块尺寸。

### 3.3 为什么 09-29 与今天"看起来不一样"——排除项(诊断)

- 请求形式:09-29 的短 yes/no 写法今天也要 16.3 秒;生产请求 17.7 秒;提示词与 JSON 约束只差 1–2 秒。
- 线程数:Ollama 今天默认 6 线程(09-29 为 12)。显式 12 线程的 5 帧中位数 14.25 秒,仅快约 15%
  (帧与时间不配对,只算线索)。
- 效率模式 / 降频:Ollama 进程未开 EcoQoS;推理时 CPU 利用率 100%+、性能指标约 200%。
- **内存紧张(未受控混杂因素)**:Ollama 每次启动时报告的可用内存 09-28 为 1.2 GiB、09-30 为
  887 MiB、今天 483 MiB;Ollama 推理期间可用内存约 0.6–0.8 GB、换页 1.3–2.6 万页/秒(Chrome 约 2.1 GB
  占主要)。所有 Ollama 数据都是在这种状态下测的。

### 3.4 受控对照:同一份 llama.cpp,只改计算位置 — n=12/档

同一个 llama.cpp b11146、同一份 GGUF(Q4_K_M + mmproj Q8_0)、同一批帧、同一提示词与 JSON schema、
`--reasoning off`、对照前已卸载 Ollama 常驻模型(可用内存约 4 GB)。

| 配置 | 640 档中位(最小–最大) | 448 档中位(最小–最大) | 预填充速度 640/448 |
|---|---|---|---|
| llama.cpp **CPU** | 13.59 秒(12.85–15.28) | 5.17 秒(4.60–5.75) | 23.7 / 35.3 token/秒 |
| llama.cpp **Iris Xe 核显**(SYCL,OpenCL 设备) | **6.49 秒**(6.06–7.69) | **3.00 秒**(2.81–4.79) | 51.2 / 71.6 token/秒 |
| (对照)Ollama CPU | 16.8 秒 | 7.7 秒 | — |

- 核显比同引擎 CPU 快 **2.1 倍(640)/1.7 倍(448)**,比生产的 Ollama CPU 快约 **2.6 倍**;
  核显 + 448 相对 Ollama CPU 640 约 **5.6 倍**(16.8 → 3.0 秒)。
- 服务端日志显示 CPU 预填充速度在同一请求内逐段下降(35→27→24 token/秒),符合持续负载下的功耗墙限速。
- 全部 24 次核显调用合法 JSON(24/24),无设备丢失崩溃。
- 输出**不是逐字相同**(640 档 3/12、448 档 1/12 相同),这是不同后端浮点差异使贪心解码分叉;内容层面
  等价:在没有杯子的帧(F00–F05)里提到杯子,CPU 4/6、核显 3/6;在手持杯子的帧(F06–F11)里提到杯子,两边都 6/6。

### 3.5 生产路径加一个环境变量:Ollama + Vulkan 核显(`OLLAMA_IGPU_ENABLE=1`)— n=12/档

Ollama 0.34.4 在设置 `OLLAMA_IGPU_ENABLE=1` 后启动,日志把 Iris Xe 识别为 `library=Vulkan … type=iGPU`
(可用 7.2 GiB),MiniCPM-V 4.6 的 25/25 层和视觉投影器(`CLIP using Vulkan0 backend`)都在核显上。
同样的 12 帧、同样的请求(`scripts/benchmark_scene_latency.py`,生产提示词 + JSON schema),
1 次丢弃的热身,无报错、无设备丢失:

| 最长边 | 单次中位数(最小–最大) | `prompt_eval` 中位 | 视觉 token | 合法 JSON | 对比 §3.1 的 Ollama CPU |
|---|---|---|---|---|---|
| 640 | **7.31 秒**(6.98–7.65) | 3.98 秒 | 294 | 12/12 | 16.8 秒 → 快 **2.3 倍** |
| 448 | **4.90 秒**(4.62–6.66) | 1.65 秒 | 151 | 12/12 | 7.7 秒 → 快 **1.6 倍** |

- 与 §3.4 的 llama.cpp(SYCL)核显相比,Ollama + Vulkan 慢约 13%(640)/ 63%(448):后端不同
  (Vulkan 对 SYCL)、请求路径不同,**差异的原因我没有拆开验证**。墙钟减去 `prompt_eval` 与生成后,
  两档都还剩约 2.2–2.3 秒没有被归因的耗时。
- 质量代理(同一个"是否提到杯子"的子串检查,助手自行核对):无杯子的 F00–F05,640 档 5/6、448 档 6/6
  提到杯子;手持杯子的 F06–F11 两档都是 6/6。与 CPU 版相比没有变好,448 档的"无依据断言"问题依旧。
- 局限:这一组**没有和 CPU 臂交错运行**——Ollama CPU 的数字来自本节之前的会话,两者的内存状态不同
  (这一组结束时可用内存仍只有约 0.4 GB)。因此"2.3 倍"是同一台机器上的前后对比,不是严格的 A/B。
- **正确性问题(重要,会改变建议)**:用 `scripts/cloud/run_cloud_suite.py` 在 24 张公开 COCO 图上做冒烟运行时,
  Ollama + Vulkan 核显有 **3/24 个输出不是合法 JSON**——模型开始吐出"文字 + 数字坐标"(类似 grounding 框的
  乱码,如 `…equipment248 203 680 950trees and grass0 0 1000 375field…`),一直写到 96 token 上限被截断。
  对这 3 张图在两个尺寸下共 6 个请求重发:**核显路径稳定复现(同样的 3 个组合失败,temperature 0 + seed 42),
  纯 CPU 路径 6/6 合法**(`outputs/ollama-igpu-20261003/recheck-igpu.jsonl` / `recheck-cpu.jsonl`)。
  用户人脸视频的 24 次核显调用全部合法,所以问题与输入内容有关;**根因未确认**(可能是 Vulkan 后端的
  数值差异,也可能是视觉块边界或图像内容触发的模型不稳定,我没有拆开验证)。
  n 很小,不能据此估计线上失败率,但足以说明:**加速 2.3 倍的同时存在输出不可用的风险**。
- 含义:生产路径**不改代码**,只需 Ollama 服务端的一个环境变量就能把推理放到核显上,但在上述
  正确性问题查清之前**我不建议把它当作默认**。这属于系统级配置,是否采用留给用户决定;默认行为本轮不改。
  代码层面的缓解办法(解析失败时自动重发一次、或回退 CPU)尚未实现和验证。

### 3.6 质量(助手自行核对;"无依据断言" = 我在画面里无法确认的物体、姿态或情绪)

| 配置 | 含无法确认断言的帧 | 手持杯子帧提到杯子 |
|---|---|---|
| Ollama CPU 640 | 4/12 | 6/6 |
| Ollama CPU 480 | 5/12 | 6/6 |
| Ollama CPU 320 | 8/11 个合法输出(另 1 个坏 JSON) | 6/6 |
| Ollama CPU 448(n=8) | 4/4 个无杯子帧都说"有杯子" | 4/4 |

**单块(≤448)带来 2.2 倍加速,同时无依据的物体断言更多**(典型是把架子说成"放着杯子")。速度不能
单独算赢;这是速度与细节的真实取舍。输出里还有结尾多余的右括号 `)` 之类格式瑕疵(640 档 2/12、
480 档 8/12、320 档 3/12),以及 ≤384 档会出现被 96 token 上限截断成坏 JSON。

### 3.7 公开图复核:云测试套件的本机冒烟运行(24 张 COCO 中的 12 张计时图 + 6 张合成圆图)

用 `scripts/cloud/run_cloud_suite.py`(只发送测试集里的公开/合成媒体)对本机两条核显路径各跑一遍,
每档 12 张不同的新图,热身 1 次丢弃。COCO 图(多数最长边 640、宽高比各异)和人脸视频帧不同,所以**绝对耗时不能和
§3.1–§3.5 直接比较**,这里只比较同一批图上的路径差异与合法率。

| 路径(同 12 张图) | 640 中位(最小–最大) | 448 中位(最小–最大) | 合法 JSON(640 / 448) |
|---|---|---|---|
| Ollama + Vulkan 核显 | 5.85 秒(5.07–9.76) | 3.15 秒(2.81–6.31) | 11/12 / 10/12 |
| llama.cpp b11146 + SYCL 核显 | 6.82 秒(6.68–11.52) | 3.37 秒(3.13–3.96) | **12/12 / 12/12** |

- 失败的 3 个输出都在 Ollama + Vulkan 路径(见 §3.5),它们对应的 3 张图在 SYCL 路径下都是合法输出;
  同样的请求在 Ollama 纯 CPU 上也是合法的。所以乱码是 **Ollama 的 Vulkan 路径特有的**(至少在这些输入上),
  不是模型或提示词本身的缺陷。根因未确认。
- 在这批图上 Ollama + Vulkan 的计时比 SYCL 略快(5.85 对 6.82 秒),与 §3.4 / §3.5 在人脸帧上
  "SYCL 更快"的方向相反;图和请求路径都不同、n=12,**不要据此声称谁更快**。能下结论的只有合法率。
- 合成圆图计数(6 张,每张圆数已知;仅为 n=6 的描述):Ollama + Vulkan 原图 4/6 计数正确、448 档 5/6;
  SYCL 原图 5/6、448 档 6/6。颜色列表完全正确的:Ollama + Vulkan 5/6 + 5/6,SYCL 4/6 + 5/6。差异在噪声范围内。
- 同时这是 `--api openai`(llama-server `/v1/chat/completions` + `response_format: json_schema`)模式
  **第一次在真实 llama-server 上的验证**:请求被接受,约束解码生效,`timings` 字段被正确解析。
  (此前只在假服务器上测过。)

结论的允许说法:**在已测配置中,llama.cpp + Iris Xe 核显 + 448(或 640)最快;生产的 Ollama + CPU
不是本地最优;只加 `OLLAMA_IGPU_ENABLE=1` 的 Ollama 核显路径比它快 1.6–2.3 倍,但在公开图上出现过非法输出
(3/24),llama.cpp + SYCL 在同样输入上 24/24 合法。**不能说"已找不到更优解":引擎、并发、llama.cpp 参数、Ollama 核显开关、OpenVINO、
更小或更好的模型都还有未穷尽的杠杆。

## 5. 局限

单机、单次会话;内存紧张未受控;对照中 CPU 臂先于核显臂运行(发热顺序对核显不利,加速比偏保守);
Ollama 与 llama.cpp 两组不是同一内存条件(前者可用内存 <1 GB,后者约 4 GB),所以"llama.cpp CPU
比 Ollama CPU 快"不能单独归因于引擎;n=12;质量为助手自行核对;测试画面只有一个人在一间屋子里。
